# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

BrandOS (branded as AIVisibility SEO / brandoseye.com / icandothat.online) is a multi-tenant local-SEO and "AI visibility" SaaS. It audits a business's website, Google Business Profile, and social presence, tracks how often the business is mentioned by AI engines (ChatGPT, Claude, Gemini, Perplexity), and ships a companion WordPress plugin that customers install on their own sites.

## Monorepo layout

pnpm workspaces + Turborepo. Packages: `apps/*` and `packages/*` (see `pnpm-workspace.yaml`).

- `apps/api` — NestJS backend (Fastify adapter), port 3001. All business logic and Prisma access lives here.
- `apps/web` — Next.js 16 (App Router, React 19) frontend, port 3000. Talks to the API only through `fetch`/`apiFetch` (see `apps/web/src/lib/api.ts`) — no direct DB access.
  - **`apps/web/AGENTS.md` is auto-generated by `next dev` on every run — do not hand-edit it or fight its regeneration; if it changes, commit it as-is.**
- `apps/worker` — standalone Node/tsx process running BullMQ job consumers (audits, AI-visibility scans, WordPress sync). No HTTP server.
- `packages/database` — the only place `schema.prisma` lives; exports a shared `prisma` client and enums (`@brandos/database`) consumed by api and worker.
- `packages/audit-engine` — shared scoring/audit logic used by both `apps/api` and `apps/worker`.
- `plugins/aivision-seo` — the WordPress plugin distributed to customer sites (PHP). `plugins/build-zip.js` packages it; `plugins/versions.json` tracks release history. The plugin self-updates from the API (see `wordpress.controller.ts` / `class-updater.php`) and reports telemetry back to `Business.wordpressTelemetry`.
- `infrastructure/` — deployment scripts (`deploy-to-vps.js`, `deploy-all.js`, `reload-vps.js`) that push builds to a VPS over SSH, plus the Docker Compose file for local Postgres/Redis.
- `ecosystem.config.js` — PM2 process definitions for production (api, web, worker) on the VPS.

## Commands

Run from the repo root unless noted. Everything is orchestrated by Turborepo.

```bash
pnpm install            # install all workspace deps
pnpm dev                # run api + web + worker in dev mode concurrently (turbo run dev)
pnpm build              # build all apps/packages
pnpm lint               # lint all apps

pnpm db:generate        # regenerate Prisma client (packages/database)
pnpm db:push            # push schema.prisma to DATABASE_URL without a migration
pnpm db:migrate         # create/apply a dev migration

pnpm docker:up          # start local Postgres + Redis (infrastructure/docker/docker-compose.yml)
pnpm docker:down
pnpm docker:logs
```

Per-app dev servers (from the app directory, or via turbo filters):
```bash
pnpm --filter @brandos/api dev      # nest start --watch (port 3001)
pnpm --filter @brandos/web dev      # next dev --turbo (port 3000)
pnpm --filter @brandos/worker dev   # tsx watch src/index.ts
```

Prisma Studio: `pnpm --filter @brandos/database db:studio`.

Building the WordPress plugin zip: `pnpm build:plugin` (runs `plugins/build-zip.js`).

Deploying to the VPS: `pnpm deploy:vps` (runs `infrastructure/deploy-to-vps.js`) — this pushes to the live production server; do not run it without explicit user confirmation.

### Tests

There is no wired-up test runner (`turbo.json` has no `test` task, no app has a `test` script). The `tests/` directory contains standalone scripts run directly:
```bash
node tests/wordpress-saas-review.test.cjs   # Node's built-in test runner (node:test); transpiles the referenced .ts files in-memory via TypeScript and stubs @nestjs/common, @brandos/database, fetch
php tests/wordpress-integration.test.php    # standalone PHP harness that stubs WP_Error/WP_REST_* and core WP functions to exercise plugin PHP files
```
When adding coverage for API/service code or plugin PHP, follow the existing pattern in these files (they load and transpile the real source file into a sandboxed context rather than importing it) instead of introducing a new test framework.

## Architecture

### Multi-tenancy

Every domain model hangs off `Business` (see `packages/database/prisma/schema.prisma`). A `User` can belong to multiple businesses via `Membership` (role: `SUPER_ADMIN | OWNER | ADMIN | MEMBER | VIEWER`). There is no `tenantId` middleware — each service method takes an explicit `businessId`/`userId` and scopes its own Prisma queries; when adding a new service, follow that pattern rather than introducing global tenant middleware.

### Auth flow

Session-cookie based, not JWT. `AuthGuard` (`apps/api/src/auth/auth.guard.ts`) reads the `brandos_session` cookie, hashes it, and looks up a `Session` row joined to `User.memberships.business`. It resolves the *active* business per-request in this priority order: `x-business-id` header → `brandos_active_business_id` cookie → `user.activeBusinessId`, but only if the user is a member of that business (or is `isSuperAdmin`); otherwise it falls back to the user's first membership. The resolved `activeBusinessId` and stripped `user` are attached to `request.user`. Controllers apply `@UseGuards(AuthGuard)` per-route (not globally) and read `req.user.id` / `req.user.activeBusinessId` directly — there's no `@CurrentUser()` decorator.

On the frontend, `apiFetch` (`apps/web/src/lib/api.ts`) always sends `credentials: "include"` and auto-attaches `x-business-id` from `localStorage` when present; `BusinessSwitcher.tsx` is what changes it.

### AI engine integration

AI-visibility scans (worker: `ai-visibility-runner.ts`, `engines.ts`) query multiple AI engines through **OpenRouter** as a single unified provider (`OPENROUTER_API_KEY`), with legacy direct provider keys (`OPENAI_API_KEY`, `PERPLEXITY_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`) only as fallback if OpenRouter isn't configured. Per-engine model overrides are set via `OPENROUTER_<ENGINE>_MODEL` env vars. Recent commit history shows this codebase deliberately moved away from synthetic/simulated/mock AI-visibility data — don't reintroduce placeholder or generated fallback data for these features.

### WordPress plugin integration

`apps/api/src/wordpress` issues API keys/secrets stored on `Business` (`wordpressApiKey/Secret`), and the plugin (`plugins/aivision-seo`) authenticates back to the API using them. The plugin self-updates (`includes/class-updater.php` + API endpoints in `wordpress.controller.ts`) and reports `wordpressPluginVersion`/`wordpressLastSyncedAt`/`wordpressTelemetry` back to the `Business` row. When bumping the plugin version, update `plugins/versions.json` and rebuild the zip with `pnpm build:plugin`.

### Billing (Stripe)

See `STRIPE_INTEGRATION_TODO.md` for the full checkout/webhook flow and required env vars. Key point: `billing.service.ts` + `billing.controller.ts` create a Stripe-hosted Checkout Session tagged with `client_reference_id`/`metadata.businessId`/`metadata.tier`, and a webhook handler mutates `Business.subscriptionTier`/`subscriptionStatus`/`stripeCustomerId`/`currentPeriodEnd` — subscription state lives entirely on the `Business` model, there's no separate `Subscription` table.

### Environment

Root `.env` and per-app `.env` (`apps/api/.env`, `apps/worker/.env`) are all loaded (see `apps/api/src/main.ts`, which loads root, then walks up two `../` levels to also pick up parent `.env` files — be aware of this when adding new env vars, since precedence depends on dotenv's "first value wins" behavior across those three loads). See `.env.example` for the full variable list (DB/Redis URLs, OpenRouter/legacy AI keys, app URLs).

Production runs on a single VPS under PM2 (`ecosystem.config.js`): `brandos-api` (3001), `brandos-web` (3000), `brandos-worker`, against `icandothat.online`. `apps/api/src/main.ts` also hardcodes the CORS allowlist for production domains (`onlinepresence.space`, `brandoseye.com`, `icandothat.online`) — update it there when adding a new production domain.
